- 評価: **A−**

## 総評

実装コードは無いが、 「設計書のリーダブルさ」 と「設計プロセスの可視性」 を品質と捉えると、 Tessera は LUDIARS 内でも高水準。 章立ては「命名 → 位置付け → 設計目標 → プロトコル → トポロジ → 接続層 → セキュリティ → crate 構成 → 依存 → テスト → マイルストーン → 未決」 と教科書的な順で、 数式・表・ASCII 図・例コードをバランスよく交える。 変更履歴を冒頭に時系列で残し (docs/DESIGN.md:7-14)、 「**いつ何を決めたか**」 をトレース可能にしている点はチームへの誠実な情報設計。

## 高評価ポイント

- **命名の必然性を §1 (docs/DESIGN.md:18-26) で書く**: ローマの tessera (合言葉 / 駒 / 客人標) と ed25519 認証ゲーム通信の対応をしっかり言語化。 README.md:5-6 にも同じ意匠が引かれており、 ブランディングが一貫。
- **比較表で位置付けを示す習慣** (README.md:11-19, docs/DESIGN.md:51-58): Synergos との対比表が冒頭にあり、 「Tessera が何でないか」 が一目で分かる。
- **数値で語る**: P50 < 50ms / P99 < 150ms (§3, docs/DESIGN.md:81-87)、 40MB/h (§6.4, docs/DESIGN.md:679-683)、 rollback 深さ 8-10 frame (docs/DESIGN.md:257)、 ARMv7 で ed25519 verify <0.3ms (docs/DESIGN.md:586) など、 「**目標値・現実値・上限値**」 が散見される。 hand-wave せず数字で議論する文化が見える。
- **「制約として受け入れる」 を明示する書き方** (§5.4.3, docs/DESIGN.md:261-277): rollback を採るとどんな制約が伝播するか (決定論 / state 予算 / one-shot event) を 3 項目で列挙。 「採用すれば良いことづくめ」 ではなく **トレードオフを明文化する** スタイル。
- **意思決定の文書化** (§5.6.5, docs/DESIGN.md:402-408 / §5.5.4 docs/DESIGN.md:306-336): tier 切替の禁止 (途中変更しない)、 プロファイル選択フローチャート、 など「**何を可逆/不可逆と扱うか**」 をはっきり書いている。 後から読む人が迷わない。
- **「解決済」 を未決事項末尾に残す** (docs/DESIGN.md:764-767): §12 の最下部に「~~~~ で取消線」 形式で過去の未決事項と解決先を書く。 議論の足跡が残るのは LUDIARS 全体でも見習いたい運用。

## 中評価ポイント

- **Markdown lint**: 軽くチェックした範囲で、 見出しスペース・table 整形・コードブロック言語指定はおおむね整っている。 ただし §5.5.4 のフローチャート (docs/DESIGN.md:308-336) が ASCII 罫線で、 mermaid 化すると GitHub プレビューでより読みやすい。
- **§5.7 が長すぎる** (docs/DESIGN.md:410-650, 約 240 行): Codex 1 節だけで全体の 30% を占有。 Codex を別リポ移行する 0.8 で要約節へ圧縮する宣言 (docs/DESIGN.md:411-412) があるので問題は把握済だが、 **現状読者にとって §5.7 が「Tessera 設計の重心」 に見えてしまう**。 早めの圧縮が望ましい。

## 低評価 / 改善余地

- **README.md が短すぎる** (21 行): 比較表 + ステータス 1 行 + 設計書リンク のみ。 LUDIARS 全リポの「最初に見る場所」 として:
  - 開発者向けの「現状」 (Codex 切り出し済 / Tessera 側 pause) を 2-3 行で
  - 関連リポ (Synergos, Codex, Tessera) のリンク
  - 設計書のセクション索引 (§5.3 経路 / §5.4 同期 / §5.6 tier / §5.7 Codex)
  …を追記すると、 リポを訪れた人の理解速度が上がる。
- **CLAUDE.md / AGENTS.md が無い**: LUDIARS 全 28 リポの中で、 設計が固まっているプロジェクトには AI 用ガイドラインを置く運用が他リポ (Memoria, Actio, Synergos) で進んでいる。 Tessera は「pause 中」 なので未整備でも妥当だが、 着手再開時には `CLAUDE.md` を追加し「`docs/DESIGN.md` が単一情報源、 §5.7 は LUDIARS/Codex 参照」 を明示すべき。
- **テスト戦略 §10 (docs/DESIGN.md:728-734)** が箇条書きのみ。 各 test profile (`tessera-sim`, NAT matrix, mobile soak, emerging-network) の具体的な pass 条件 (P50/P99 数値、 切断回数、 収束時間) が無く、 「やってみないと PASS/FAIL が判断できない」 状態。 数値 KPI を埋めるべき。
- **マイルストーン §11 (docs/DESIGN.md:737-747)** に **time estimate が無い**: 「M0 = 1 週間 / M1 = 2 週間 / M3 = TURN 完遂後 1 週間」 などの目安があると、 再開時の planning に使える。
- **「v0.7 で pause」 をリポ ROOT で見つけにくい**: README.md にステータスは書かれている (README.md:22-24) が、 「pause した理由 = Codex 切り出し」 が DESIGN.md の中まで読まないと分からない。 README に 2 行追記推奨。
